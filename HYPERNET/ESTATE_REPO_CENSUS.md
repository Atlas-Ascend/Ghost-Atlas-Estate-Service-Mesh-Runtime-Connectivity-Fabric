## 2. Render Hypernet — runtime body

Observed live Render service inventory is maintained separately in `LIVE_CLOUD_SURFACES.md`. Render consumes approved GitHub source and emits runtime health, request, deployment and proof events back through the Event Gateway / Observatory path.

## 3. Vercel Hypernet — public/edge/UI body

Vercel owns frontend/public edge surfaces and preview/production UI deployments. It does not own backend truth or canonical state.

## 4. Neon Hypernet — durable state body

Neon owns relational persistent state for enrolled applications and registries. Database state must be addressed by capability/contract, never by repo-name coupling.

## 5. Eden Hypernet — local sovereign runtime body

EDEN is the local runtime/hardware-capability bridge. It may provide local models, filesystem operations, device access and local compute through registered capabilities. It is not the cloud control plane.

## 6. Hardware + Software Hypernet — physical body

Declared physical nodes are enrolled through VISHVARUPA/Eden capability contracts: JANUS phone, ODIN phone, EDEN local node, T5810-1, T5810-2, GA-ARK tiers and future robotics/IoT nodes. Hardware never receives authority merely by being reachable; calls remain JANUS-authorized, CrownGrid-routed, registry-resolved, mesh-transported and SECA-auditable.

# Failure and proof route

```text
REQUEST
  -> JANUS authorization
  -> CrownGrid capability route
  -> Service Catalog provider resolution
  -> Service Mesh invocation
  -> provider executes on Render / Vercel / Neon / Eden / hardware
  -> Event Gateway normalizes lifecycle events
  -> Runtime Observatory exposes state
  -> SECA inspects evidence

failure at coding/build      -> DEVOS + MetaForge family
failure at provider/runtime  -> mesh failover / runtime control plane
failure at security          -> Medusa / Heimdall
failure at state/schema      -> owning service + Neon migration workflow
failure at proof/quality     -> SECA FAIL; no promotion
failure at authority         -> JANUS deny; no execution
failure at routing           -> CrownGrid/registry/mesh diagnostics
```

## Promotion rule

A repository is **not** considered connected merely because it appears in this census. Full connected status requires:

1. repository enrolled in the service/capability registry where it exposes a runtime capability;
2. explicit producer/consumer contract;
3. runtime endpoint or declared non-runtime role;
4. telemetry/event path;
5. security classification;
6. SECA evidence class and acceptance gate;
7. deployment/publication mapping where applicable;
8. no unresolved authority conflict.
